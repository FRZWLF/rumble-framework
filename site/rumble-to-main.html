Lumos · how the work works

From a rumble to a green main.

One developer, one product, a set of specialised agents — and a way of working in which a design conversation becomes a contract, the contract becomes a pull request, and every decision on the way is written where the next session will find it.

01Three kinds of session

The conversation is not the workbench.

Thinking, orchestrating and building live in sessions with their own context. They hand over through GitHub and the docs — never through chat history. That is what makes the work resumable, reviewable and affordable.

Rumble session

Think, decide, write it down

Rico and Claude rumble a requirement against the platform reality — what iOS allows, what a wall screen may show, who owns a card. Conclusions become D-rows, open questions G-rows, numbers M-rows.

/task-out
context carriedgrows with the talk

Ends at task-out. It never triages, designs or builds.

Pipeline session

Orchestrate, don't read code

A fresh session picks the free issues off the umbrella, spawns the agents, reads their verdicts, resolves merges and posts the trail. Its context stays small because it delegates every line of code reading.

/pipeline 232  ·  /pipeline
context carriedthin, per arc

Runs waves of ≤ 3 builders; retires when the umbrella is done.

Agent sessions

One job, one worktree, one verdict

Triage, architect, implementer, reviewers — each starts from zero with only the issue, the design comment and the standards. They read deeply, work in an isolated git worktree, and end with a PR or a VERDICT: line.

02Rumble → contract

A design talk condenses into an issue an agent with zero context can build.

Task-out distils a rumble into one issue per shippable unit. The issue is the whole contract: if an implementer would need to ask a question the rumble already answered, the draft is rejected. Choices the rumble made are written as decisions, not options.

03Three tables

Decisions, gaps and numbers have rows — never just memories.

Every rumble and every PR leaves rows that code, tests and issues cite by id. Numbers are reserved in the issue so parallel designs cannot collide, and a test walks the tree to make sure every citation has a row.

Is this buildable by someone with zero context?

Triage reads the issue against the standards: goal, testable acceptance criteria, scope boundary, test expectation, no open questions. Delegated architecture (a reserved D-row) is not an open question — it is the architect's brief. Then it stamps the routing labels.

# the only writes triage makes
gh issue edit 229 --add-label area:voice,size:L,risk:high,claude:build
# or: needs-human · blocked

Read everything once, so nobody rediscovers it.

The architect reads the issue and the tree, then posts the plan: approach, contracts, the reserved D-row's text, a step plan with a green board after each step, the reviewer's risk points, the implementer model. It never writes code. Its findings are where surprises die early — "neither app holds an events socket yet", "the Secure-Enclave key cannot be exported, so the signer is a foreign trait".

🏛 Design · D-234 · needs: opus · 3 PRs

An isolated worktree, a branch, a draft PR.

The implementer follows the design, verifies before it opens the PR, and writes into the PR body what the reviewers build on: the suites it ran, the mutations it tried, the doc rows it added. Model by size — sonnet for S, opus for M and L, fable only on the architect's explicit ask.

Two lenses. Every finding verified before it is reported.

The quality reviewer checks correctness, safety of AI actions, reuse, docs discipline. On risk:high a security reviewer runs in parallel — input handling, policy bypass, injection surface, secrets, transport. Reviewers reuse the PR's evidence: the named suites plus at most two mutations of their own. The report ends in one machine-readable line.

VERDICT: findings (1 red, 5 nits)

Fix the reds, answer the nits, prove it with a mutation.

The same implementer returns with the findings verbatim. A 🔴 is fixed on opus; a nit-only round runs on sonnet. The reviewer that held the 🔴 re-reviews for new reds only. After two rounds an open 🔴 escalates to Rico — the only inbox.

Clean means merged — in Rico's name.

Ready, squash-merge, pull main, run the full board once on main. Red on main means revert and escalate. On risk:medium|high Rico is assignee and reviews after the fact via the trail. Merging main into a branch is the orchestrator's job — resolve, verify, then commit.

05Documentation discipline

The docs are the memory — and a test keeps them honest.

Nothing relies on remembering. A test called doc_anchors walks the whole tree on every board: every D-, G-, M- reference must have a row, every relative link must resolve, and several unit tests read the docs for numbers they pin. Documentation is part of "done".

06The critical axis · D-224 → D-226

A prompt change cannot ship without proving it made no new misaction.

Lumos can unlock doors. So the eval corpus carries a critical axis — sentences where the only right answer is a refusal, a question back, or exactly one call in the right tier — and a deterministic runner replays recorded model answers offline. A fingerprint over the whole first prompt round makes every fixture stale the moment the prompt moves.

The rule the pipeline enforces (D-226)

Any diff that touches the prompt assembly, the decision table or a tool the model can be offered makes cargo test --test eval critical a mandatory part of the board. A red run is a 🔴 of the review, not a nit. A stale fixture is re-recorded in the same PR, and the PR says why. The baseline is pinned by name — three known misactions of the local model, published, not hidden — so a fourth turns the board red, and so does a pinned case that quietly stops misacting.

07M-080 · where the tokens go

The review loop is the value. The session is the cost.

Sixteen PRs, ~34 million tokens, a ledger per stage. Every first review found a real finding, so reviews stay. What the ledger could not see was the orchestrator itself — one session carrying a rumble and two arcs re-sends its whole history on every turn. Four structural levers halve the bill without touching the model table or the review rules.

09The loop

State lives on GitHub. Knowledge lives in the docs. Sessions are disposable.

A rumble can be closed the moment its issues exist; a pipeline session can be retired after every wave; an agent is gone the moment it reports. What survives is what the next reader needs: the issue, the design comment, the PR discussion, the trail — and three tables of decisions, gaps and numbers.
